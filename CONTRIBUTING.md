# Contributing to GitHub Templates

Thank you for improving these examples! This is a curated collection of GitHub community files and workflow samples, not an application with a shared runtime.

## Before opening a pull request

- Choose one template or workflow and explain the concrete problem it fixes.
- Check whether a proposed GitHub Actions version, syntax or security setting is still supported.
- Keep samples generic. Replace personal addresses, credentials, placeholder keys, unsupported support dates and employer names with explicit instructions for the destination maintainer.
- Do not introduce secrets, tokens or real user data into examples.
- If a change affects a destination project's license, branch policy, access controls or security promises, explain that it needs an explicit owner decision.

## Pull request checklist

1. Explain who should use the template and where GitHub expects the file to live.
2. Include a small example of expected behavior or a link to the relevant official documentation.
3. Confirm any affected YAML/Markdown is syntactically valid.
4. Document assumptions about repository permissions, runners or third-party GitHub Actions.
5. Link to the relevant issue when one exists.

Please follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). Security concerns should be reported privately using [SECURITY.md](SECURITY.md).

Maintainer review is based on the scope and safety of the change; this repository does **not** require an invented fixed number of external reviewer approvals.
